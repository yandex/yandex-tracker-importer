# AGENTS.md — руководство для ИИ-агента: импорт данных в Yandex Tracker

Ты помогаешь пользователю загрузить в **Yandex Tracker** данные, подготовленные в
универсальном YAML-формате (например, выгрузку из
[`trello`](exporters/trello) или собранные вручную). Конвейер:

```
data/*.yaml  →  importer (этот проект)  →  Yandex Tracker
```

> **ВАЖНО — это запись в боевой Трекер.** Импортёр СОЗДАЁТ очереди, задачи,
> комментарии, вложения и т.д. Откатить массово это трудно. **Всегда** сначала
> прогоняй на тестовой организации/тестовых очередях и явно подтверждай запуск с
> пользователем. Никогда не запускай импорт «молча».

---

## Что спросить у пользователя

1. **Каталог `data/`** — результат экспортёра (или ручной). Без него импортировать
   нечего.
2. **Адрес API** — по умолчанию `https://api.tracker.yandex.net`.
3. **OAuth-токен Трекера** — приложение на <https://oauth.yandex.ru> со scope
   `tracker:read` + `tracker:write`.
4. **ID организации** — ровно одно из двух:
   - `dest_org_id` — для организации **Яндекс 360**;
   - `dest_cloud_org_id` — для организации **Яндекс Облака**.

> Токен — секрет: не выводи в логи, не коммить, предложи перевыпустить после импорта.

## Рабочая директория

```
config.yaml        # доступы (см. ниже)
data/              # что импортируем (из экспортёра)
mapping/           # сопоставления *.cfg (см. ниже)
logs/              # создаётся автоматически
```

### `config.yaml`

```yaml
dest_tracker_api: https://api.tracker.yandex.net
dest_tracker_token: <OAuth-токен>
dest_org_id: "<id>"          # ИЛИ dest_cloud_org_id — ровно одно из двух
```

### `mapping/*.cfg` — сопоставления

Формат: по строке `<исходный_ключ>:<целевой_ключ>`; пустые строки и `#` —
игнорируются. Если ключа нет в файле — используется исходное значение.

| Файл | Обязателен | Что сопоставляет |
|---|---|---|
| `users.cfg` | да | пользователи → **логины Трекера** (см. ниже) |
| `queues.cfg` | да | ключи очередей |
| `statuses.cfg` | да | ключи статусов |
| `resolutions.cfg` | да | ключи резолюций |
| `issue_types.cfg` | да | ключи типов задач |
| `priorities.cfg` | нет | приоритеты |
| `fields.cfg` | нет | ключи глобальных полей |
| `local_fields.cfg` | нет | ключи локальных полей |
| `groups.cfg` | нет | названия групп |

**`users.cfg` — самое важное.** Экспортёры кладут пользователей по e-mail или
имени (не по логину Трекера). Помоги пользователю его собрать:

1. Собери уникальных пользователей из `data/` (поля `createdBy`, `assignee`,
   `followers`, авторы `comments`/`worklogs`/`attachments`, `lead`, `teamUsers`).
2. Для каждого предложи строку `<как в data>:<логин в Трекере>`.
3. Незамапленные значения уйдут в Трекер как есть и, скорее всего, не найдутся —
   надо замапить всех: можно маппить отсутствующих в какую-то заранее оговоренную учетку по умолчанию.

## Запуск

```bash
docker build -t yandex-tracker-importer:latest .      # либо podman build …

docker run --rm -v "$(pwd)":/work -w /work yandex-tracker-importer:latest
```

Флаги передаются после имени образа:

| Флаг | Назначение |
|---|---|
| `--data-dir <dir>` | каталог с данными, если он не `data` |
| `--log-level DEBUG` | подробный лог для разбора ошибок |
| `--max-workers <N>` | число параллельных потоков |

Например: `docker run … yandex-tracker-importer:latest --log-level DEBUG`.

**Dry-run отсутствует** — единственная страховка это тестовая организация. Начни с
ОДНОЙ маленькой очереди на тесте, проверь результат в интерфейсе Трекера, и только
потом запускай остальное. Логи каждого прогона — в `logs/import-<дата>.log`.

## Поэтапный импорт

Можно докладывать файлы в `data/` и запускать повторно. Импортёр идемпотентен по
ключу: уже созданную задачу он находит и **пропускает целиком**, а не создаёт
заново (значит и дублей не будет).
- **Не удаляй** уже загруженные файлы между этапами — они нужны для связей.
- Поэтапно можно докладывать НОВЫЕ: проекты, портфели, цели, очереди, компоненты,
  версии, локальные поля, триггеры, макросы, задачи.
- **Комментарии, вложения, чек-листы, ворклоги** создаются только вместе с самой
  задачей (в момент её создания). Отдельного пути «дозалить/обновить» их у уже
  импортированной задачи нет — повторный прогон её пропустит. Дубли появятся лишь
  если задача **создаётся заново** (её удалили в Трекере или сменился её ключ —
  напр. правка `queues.cfg`).

## Проверка

Импорт **не останавливается** на ошибке отдельного объекта: каждый объект
обрабатывается независимо, ошибка пишется в лог, а прогон продолжается. Поэтому
успех определяется не кодом возврата, а результатом:

- открой созданную очередь и несколько задач в интерфейсе Трекера — проверь
  статусы, исполнителей, комментарии, связи, вложения;
- пройди по `logs/import-<дата>.log` и найди `ERROR`/`exception` — это
  пропущенные объекты (частая причина — незамапленный пользователь или
  отсутствующий статус/тип). Исправь `mapping/*.cfg` или данные и перезапусти.

## Безопасность

- Импорт **пишет** в Трекер — подтверждай запуск, начинай с теста, малого объёма.
- Токен не сохраняй в репозиторий; предложи перевыпустить после миграции.
- Формат входных файлов описан в [`docs/`](docs/) — свериться при ручной правке.
