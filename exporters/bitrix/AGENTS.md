# AGENTS.md — руководство для ИИ-агента: миграция Bitrix24 → Yandex Tracker

Ты помогаешь пользователю перенести задачи **Bitrix24** в **Yandex Tracker**. Этот инструмент (`bitrix_exporter`)
выгружает задачи, рабочие группы и потоки Bitrix24 в YAML, совместимый с универсальным импортёром
[`yandex-tracker-importer`](https://github.com/yandex/yandex-tracker-importer).
Полный конвейер:

```
Bitrix24 REST API  →  bitrix_exporter (этот проект)  →  data/*.yaml  →  yandex-tracker-importer  →  Yandex Tracker
```

Экспортер **только читает** Bitrix24 и пишет файлы — ничего не меняет ни в Bitrix24, ни в Трекере. Заливкой в
Трекер занимается отдельный импортёр `yandex-tracker-importer`.

---

## Что спросить у пользователя

1. **Входящий вебхук Bitrix24** — адрес вида `https://<портал>.bitrix24.ru/rest/<id>/<код>/`. Вебхук создаёт
   администратор портала. Вебхуку нужны все доступные права: без прав на группы, диск и чаты задач эти данные не
   выгружаются.
2. **Что переносить** — все задачи или часть: по группе, по дате, по статусу. Можешь помочь составить список групп
   или фильтр (см. «Шаг 1»).

> Вебхук — секрет: не выводи его в логи, не коммить в репозиторий, предупреди пользователя перевыпустить код
> вебхука после миграции.

---

## Шаг 1. Discovery — помоги составить фильтры

С вебхуком перечисли рабочие группы и посмотри, сколько в них задач:

```bash
curl "<вебхук>sonet_group.get.json?IS_ADMIN=Y"
curl "<вебхук>tasks.task.list.json?filter[GROUP_ID]=<id группы>&select[]=ID"
```

Группы для переноса перечисли в `configs/.projects` — по id в строке. Фильтры — поля `tasks.task.list` для задач и
`socialnetwork.api.workgroup.list` для групп, например `GROUP_ID: 123` или `CLOSED: "N"`.

## Шаг 2. Собери образ

```bash
docker build -t bitrix-exporter:latest .    # либо podman build …
```

## Шаг 3. Подготовь `configs/` и запусти

```
configs/
├── webhook_url.cfg         # входящий вебхук
├── tasks_filter.yaml       # фильтр задач, {} — все; с .projects — сужает задачи групп
├── projects_filter.yaml    # фильтр групп, {} — все
└── .projects               # или: id рабочих групп по строке, выгружаются вместе с задачами
```

```bash
docker run --rm --user "$(id -u):$(id -g)" -v "$(pwd)":/work -w /work bitrix-exporter:latest
```

**Совет:** начни с одной небольшой группы в `configs/.projects`, проверь результат, потом допиши остальные группы и
запусти экспорт снова: выгруженные группы записаны в `state/projects.cfg` и с тем же `tasks_filter` пропускаются.
Повторный экспорт в тот же каталог дополняет выгрузку: ключи очередей потоков сохраняются в `state/flows.cfg`, связь
подзадачи с родителем восстанавливается, в каком бы порядке ни выгружались их группы.

## Шаг 4. Проверь выгрузку

- `data/queues/<KEY>/queue.yaml` — очередь потока; задачи без потока — в очереди `TASK`, эпики скрама — в `EPIC`;
- `data/queues/<KEY>/<KEY>-N/issue.yaml` — задачи (рядом `attachments/`), `N` — номер задачи в Bitrix24, у эпиков —
  id эпика;
- `data/projects/<id>/project.yaml` — рабочие группы;
- `data/{statuses,resolutions,categories,global_fields,boards}.yaml` — справочники и доски скрам-групп;
- `info/users.csv`, `info/departments.csv` — списки для сопоставлений;
- `state/flows.cfg`, `state/projects.cfg` — состояние для повторного запуска; не удаляй их между запусками.

Открой пару `issue.yaml` и убедись, что `summary`/`status`/`assignee`/`comments` выглядят осмысленно.

В конце экспорт печатает сводку ошибок; при ошибках код завершения — 1, подробности — в `logs/`.

## Шаг 5. Импорт в Tracker (через `yandex-tracker-importer`)

Готовые `data/` заливает импортёр `yandex-tracker-importer` (отдельный проект). Ему нужны файлы сопоставлений
в `mapping/`:

- `users.cfg` — идентификатор из `info/users.csv` → логин Трекера для каждого `bitrix-user-<id>` и для пользователя,
  которого нет в организации Трекера под этой почтой. Это ключевой ручной шаг;
- `groups.cfg` — отделы из `info/departments.csv`, если группа в Трекере называется иначе, и строка
  `Все сотрудники:1`, если в выгрузке есть потоки, где ставить задачи могут не все;
- `queues.cfg` — `TASK`, `EPIC` и ключи из `state/flows.cfg`, если в Трекере очереди называются иначе; название
  потока — в `data/queues/<KEY>/queue.yaml`;
- `statuses.cfg`, `resolutions.cfg`, `issue_types.cfg`, `priorities.cfg`, `fields.cfg`.

Формат строки — `<ключ в выгрузке>:<ключ в Трекере>`. Строка нужна только для ключа, который в Трекере другой.
Файлы `users.cfg`, `queues.cfg`, `statuses.cfg`, `resolutions.cfg`, `issue_types.cfg` обязательны, даже пустые;
`groups.cfg`, `priorities.cfg`, `fields.cfg` — по необходимости. Дальнейшие детали — в
[документации импортёра](https://github.com/yandex/yandex-tracker-importer).

## Карта соответствий (кратко)

| Bitrix24 | Yandex Tracker |
|---|---|
| Задача | Задача (`issue.yaml`) |
| Поток | Очередь; без потока — очередь `TASK` |
| Рабочая группа | Проект; закрытая или невидимая — доступ только команде |
| Статус | Статус и резолюция |
| Комментарии ленты и чата задачи, результаты задачи, файлы | `comments`, `attachments` |
| Чек-листы | `checklistItems` |
| Учёт времени | `worklogs` с автором и временем создания |
| Пользовательские поля | Глобальные поля |
| Стадия канбана | Поле `kanbanStatus` |
| Скрам-группа | Доска со спринтами и бэклогом, `storyPoints`; эпики — задачи в очереди `EPIC` |
| Владелец и модераторы группы, отделы | Ответственный и права проекта |
| «Кто может ставить задачи» в потоке | Право создания задач в очереди |

Полное описание полей и нюансов — в [`docs/`](docs/index.md).

## Ограничения (проговори пользователю заранее)

- **Пользователи** переносятся по почте; пользователь без почты — идентификатором `bitrix-user-<id>`. Такого
  пользователя и пользователя, которого нет в организации Трекера под этой почтой, нужно сопоставить с логином в
  `mapping/users.cfg`.
- **Отделы** попадают в права по названию группы Трекера; импортёр групп не создаёт.
- **Доски канбана групп** не переносятся: стадия задачи хранится в поле `kanbanStatus`.
- **Не переносятся:** связи диаграммы Ганта, история изменений.

## Безопасность

- Не выполняй разрушительных операций; экспортер работает только на чтение Bitrix24.
- Всегда проверяй результат на небольшой группе до полной выгрузки.
- Вебхук не сохраняй в репозиторий; предложи перевыпустить его код после миграции.
